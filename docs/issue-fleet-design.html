Issue 驱动：Issues 页里的 session

设计稿 · 2026-09-13 · 面向 [[issues-view]] / [[issues]] / [[session-nesting]] / [[mentions]]

一句话：Issue 是任务的锚，session 是干活的人。把「谁在为这个 issue 干活」做成 session 记录上的一根指针 issue——和 parent 是同一种东西：创建时写一次，读时派生——Issues 页面就能长出一个 fleet 栏，而所有对 session 的操作（关闭、退役、看子会话、验收合并）全部复用 dashboard 已有的零件。

1. 数据模型：一根指针，不是一张表

session.issue: string | null —— 这个 session 为哪个 issue 而存在。放在 session 侧而不是 issue 侧，原因有三：

  • 存储位置：session 记录在全局 store（session application），改它零成本；local issue 是 git 提交的 markdown，每次指派要一个 commit；forge issue 在 GitHub 上，根本放不下本地 session id。放 session 侧，对两种 store 的 issue一样有效。
  • 基数对：一个 worker 一个 worktree 一个任务，所以 session→issue 是 0..1；issue→sessions 是 0..n，由 join 得到。和 parent 完全同构。
  • 不发明第二种东西：它就是 provenance。parent 答「谁生的我」，issue 答「我为什么被生出来」。读时派生、不推断 lifecycle、不写回 issue，三条纪律都照搬 nesting 的。

写入：三条路，都走同一个 create boundary

① @new 在 issue 线程里dispatchNewMentions 手上已经有 ctx.threadId，把它作为 issue 传进 sessionCreateRequest。零新机制，一行。
② spex session new --issue <id>dashboard 侧栏的「New worker」按钮就是它的按钮形态；不新增 @issue: 这种语法动作。
③ spex issue assign <issue> <SEL>把已存在的 session 挂上来 = 写指针 + 一次现有 session send（把线程发给它，prompt 与 originator loop-in 同形）。它是 reparent 的孪生：reparent 动 parent，assign 动 issue。可重指向别的 issue；「解除」留给真实需求出现再做。

派生（读时，前端一个纯函数）

// issueFleet(issue, sessions) —— [[session-nesting]] 的同一套树，只是从另一个入口进
assigned    = sessions.filter(s => s.issue === issue.id)
fleet       = assigned ∪ 它们的全部后代（nestSessions 的 childrenOf 递归）
participants= {issue.by} ∪ replies[].by 中能 resolve 到 session、且不在 fleet 里的
workState   = rollup(fleet)：need（任一 asking/review/done/error/close-pending）
            > run（任一 working/parked） > offline（全 offline/retired） > none（无 fleet）

子 session 不需要再写 issue 指针——它属于父的 fleet 是树给的，和「父关闭子自动升根」同一条读时规则。workState 就是 subtreeRollup 的逻辑用在 issue 上；它不存储，不改 issue 的 open/closed。

2.3 线程就是验收台账（v2）

不新增写路径。issue-bound session 的每次声明（done --propose / ask / park）已经通过 hook 写进了它自己的记录；线程渲染时把 fleet 的声明读时合并成系统行（上图斜体那行），按时间与 replies 交错。这就对应 openteams「Work mode 主时间线只放需求确认 / 冲突升级 / 结果验收」——但我们不用 agent 往 issue 里写一条消息，而是把它本来就写过的状态投影进来。

v1 的验收动作只有两个、都已存在：session 行上的 Merge，composer 里的 Close issue。merge 完 session 读作 retired（旗子），人点 Close 清掉；issue 仍要人 close——[[state]]「merge 与 close 人做」一字不动。

3. 需要你拍板的一点：@session 要不要变成指派

你的原话：「用户可以 @ 他的 session」——预期 @ 就是指派。现行 spec（[[mentions]]）：@session 是被动引用，「mentioning it never … wakes its harness, creates a worker, or changes state」；spec 里还记着一次事故——issue 正文代码块里的 @new 真的派出了一个 worker。

我的建议：保留被动，指派走显式的门。理由：这条语法已经写进每个 agent 的 prompt 和存量线程；给它加副作用，所有历史文本里的 @ 会在下一次渲染/重放时突然「做事」。指派用侧栏 Assign 门 + spex issue assign verb 承担，语义一眼可见。

折中方案（推荐）：composer 草稿里出现 @<某个 live session> 时，action row 亮起一个一次性按钮「Send to @x」——文本不变，动作是显式点击，且是现有 session send。这样「@ 他的 session 然后发过去」的手感有了，语法没动。

三个选项：A 保留被动 + Assign 门；B A + composer 里的显式「Send to @x」按钮（推荐）；C 改 spec，让 issue 线程里的 @session = assign + send。

6. 对照 openteams

来源：README、docs/core-features/chat-session-overview.mdx、ai-members.mdx、OpenTeams-Technical-Documentation.md（2026-09-13 抓取）。Issue↔session 的机制在其文档里基本是空的：README 只说 "developer-controlled Issues … link work to agent sessions"，技术文档没有 Issues 章节，Work mode 标注 v0.4.0 计划中。

openteams我们差别
Chat session = 工作台；成员在里面被 @ 指派Issue = 任务锚；session = 一个 worktree 里的 worker他们的「会话」是聊天室，我们的 session 是有分支、有 worktree、能 merge 的工作单元；所以我们的验收是 git 事件，不是一条消息
成员状态 Idle / Running / Completed / Failed（技术文档：idle / running / waiting_approval / dead）working parked asking review done error idle offline retired… 两轴（lifecycle × liveness）我们已经更细，且 asking/review 是「等人」的显式态——这正是 issue 页最该高亮的；不引入他们的四态
@mention 即指派@session 被动；@new 创建；指派走显式门（§3）唯一的实质分歧，见 §3 的三个选项
Work mode（计划）：lead agent 拆任务、并行执行、主时间线只放需求确认 / 冲突升级 / 结果验收parent/child 树已存在；线程读时合并声明（M3）思路一致；我们不用 agent 往 issue 写消息，而是投影它本来就写过的状态——少一条写路径
Task message 交付最终产出session 的 files/web/widgets 在展开卡里产出挂在 session 上而不是消息上，merge 后仍可追溯
Build statistics（资源、成本）无暂不做；若做也是 session 属性，读时进卡
